# PIPELINE — план многоагентной работы над Neo Library

**Создано:** 2026-10-16. **Статус:** последовательность ролей согласована с пользователем.
Связанные файлы: `CONTEXT.md` (общий контекст), `ISSUES.md` (интерфейс конвейера: тикеты и
состояния), `skills/tests/SKILL.md` (база скила тестировщика).

## 1. Роли

| Роль | Агент (OpenCode) | Скил | Права (permissions) |
|---|---|---|---|
| **A** — аналитик | `analytics` | `analytics` (новый) | чтение кода; запись только `.agents/ISSUES.md`; prod-код и тесты не трогает |
| **T** — тестировщик | `tests` (агент) | `tests` (существующий) | пишет только `app/src/test/**`; prod-код не трогает |
| **D** — разработчик | `develop` | `develop` (новый) | пишет только prod-код; тесты не пишет и **не правит** |
| **R** — рефактор | `refactor` | `refactor` (новый) | prod-код; тесты не трогает, публичный API не меняет |
| **H** — человек | — | — | гейты: план, блок-вопросы D, merge |

Механика OpenCode: роль = определение агента (`.opencode/agents/<name>.md`: system prompt —
краткое описание роли + permissions), знание = скил (`.agents/skills/<id>/SKILL.md`).
Per-agent permission на скилы (allow/deny) — матрица: A видит только `analytics`,
T — `tests`, D — `develop`, R — `refactor`; скил `tests` доступен D и R для **прогона**
сьюта (reading, не authoring).

## 2. Поток 1 — фича/фикс (основной)

```
H: задача
  → A: план = тикет [FEATURE]/[FIX] в ISSUES.md
  → H: СОГЛАСОВАНИЕ плана (гейт №1; до согласования T/D не стартуют)
  → T: тесты по плану (к моменту записи — RED, это нормально)
  → D: код, чтобы тесты прошли (GREEN)
        ├─ блок-проблема            → стоп → вопрос к H
        ├─ тест T «неправильный»    → не трогать → вопрос к H (правит T/A)
        └─ проблема низкого прио-  → новый тикет в ISSUES.md → продолжить
  → верификация: полный сьют зелёный + lint 0 errors + assembleDebug
  → push (pre-push сам гоняет сьют) → PR → merge в master (H, branch protection)
```

### Правила протокола (последствия test-first)

1. **План A обязан содержать раздел «Тесты»**: какое поведение/инварианты/граничные
   случаи прибивают тестами — это и есть ТЗ для T. Без раздела T не имеет основания.
   Шаблоны: ISSUES §14 (готовый план) + скил `tests` §5 (инварианты, которые закреплять).
2. **Test-first**: тесты пишутся до кода и становятся спецификацией задачи. Коммит с
   красными тестами T **разрешён** (pre-commit гоняет только lint, он зелёный),
   но **push — только после GREEN D** (pre-push гоняет сьют и не пустит push с красным).
3. **D не имеет права менять тесты T**, чтобы они прошли (классическая TDD-ловушка —
   тест-резином). Тест противоречит плану/реальности → вопрос к H; правит тест T (по
   исправленному плану A), D — только prod-код.
4. **Один шаг плана = один коммит** (устоявшаяся практика проекта, см. ISSUES 6.x–14).
5. **Документация**: изменение заделало задокументированный факт (class map, workflow,
   инвариант, UI-числа) → `CONTEXT.md` обновляется тем же коммитом (урок 13.2).
6. Состояние тикета в `ISSUES.md` отражает этап потока: `план → тесты → код → готово`
   (внутри привычных `[ ]`/`[~]`/`[x]` + строка «Статус» в шапке тикета).

### Дерево решений D при проблемах

| Проблема | Действие |
|---|---|
| Задача заблокирована (план не реализуем, впереди инвариант, тест не сделать честным путём, crash/потеря данных) | Стоп → сразу к H |
| Тест T ошибочен / противоречит плану | Не править → H (коррекция тестом T, при необходимости план — A) |
| Новая проблема низкого приоритета (не блокирует задачу, не бьёт по инвариантам) | Тикет в `ISSUES.md` (`[FIX]`/`[IMPROVE]`, низкий) → продолжить задачу |
| Улучшение/задел «попутно» вне плана | Не делать; максимум — тикет в `ISSUES.md` |

## 3. Поток 2 — рефакторинг (отдельно, по требованию H)

```
H: «рефакторинг X»
  → нет утверждённого [REFAC]-тикета? → A пишет его (или R чернит → H утверждает)
  → R: рефакторинг по шагам тикета: каждый шаг = коммит + полный сьют зелёный
  → T: проверка: полный сьют (с правилом флейков 8.4), lint, assembleDebug,
       набор тестов не изменился
```

- Инварианты R: поведение не меняется, **публичный API не меняется**, стиль (pre-lambda)
  не трогать, один шаг = один коммит, **тесты не править** (тест «мешает» = рефакторинг
  сломал контракт → стоп → H).
- Задача T после R — safety net: те же тесты, те же assertions, все зелёные; сьют
  не пополнился и не осиротел. Флейк-правило 8.4 (таймаут в полном сьюте → сначала
  изоляция, не регресс).
- Желательно — отдельная ветка/worktree, чтобы не конфликтовать с потоком 1
  (протокол 10.2: `git status` + mtime файлов до начала правок).
- Текущий утверждённый кандидат: тикет `[REFAC]` «MetaExtractor/CoverExtractor»
  (план утверждён, рефакторинг не начат — см. `ISSUES.md`).

## 4. Человеческие гейты (итог)

1. Одобрение плана (A→H) — до старта T.
2. Блок-вопросы D (по дереву решений §2).
3. Р: само требование H + утверждение `[REFAC]`-тикета, если его не было.
4. Финальный merge в master: PR + branch protection + pre-push (автоматика уже в репо:
   pre-commit = lint, pre-push = полный сьют + запрет прямого push в master).

Автоматических гейтов в конвейере достаточно, чтобы человек не сидел в контуре
каждого коммита — только в четырёх точках выше.

## 5. Контексты и скилы (результаты анализа, подтверждены)

- **`CONTEXT.md` не дублируется на агента.** Общий ядро (~110 стр.): суть, форматы,
  стек, two-layer model, class map, workflows, **инварианты (полный список — один
  источник)**, build/run + указатели. Различие ролей несёт скил, а не копия контекста.
- **Унести из `CONTEXT.md` в скил `develop`**: детали grid/пагинации/свайпа (~63 стр.)
  и SVG→PNG-тулчейн иконок (~23 стр.).
- **Скилы**: `analytics` (новый), `develop` (новый), `refactor` (новый),
  `tests` (существующий — это и есть база роли T, новый скил тестировщику не нужен).
- **README.md vs CONTEXT.md**: зафиксировать владельца каждого факта (в табл. выше),
  иначе третий инцидент дрейфа (6.5/13.2) — вопрос времени.
- **`ISSUES.md`** — интерфейс конвейера: тикет = самодостаточная задача
  (диагностика, шаги, «как проверять», анти-рекомендации, состояние).

## 6. Что изменилось относительно первой версии отчёта

1. Тестировщик — **отдельная роль** (не «опциональный вариант b»): `tests`-скил
   переиспользуется как есть.
2. Порядок: A → **T** → D (test-first): тесты пишутся до кода и являются спецификацией
   задачи; D пишет код «на тесты».
3. В план A обязан входить раздел «Тесты» — основа для T.
4. Новая жёсткая граница: **D не правит тесты T**; проблемы D → H (блок) или
   `ISSUES.md` (низкий приоритет).
5. Рефакторинг: R → **T** (проверка после рефакторинга); R не трогает тесты.
6. Протокол коммитов/push: красные тесты T — коммит можно, push только после GREEN.
