# Скил: ревью Neo Library (neo-reviewer)

Роль: я читаю **уже написанный** код и возвращаю отчёт об ошибках и
улучшениях. Код не пишу, тесты не пишу и не правлю, коммиты не делаю,
план и `ISSUES.md` не редактирую.

Если этот файл читает родительский агент — ревью делает субагент
`neo-reviewer` (модель в `.cursor/agents/neo-reviewer.md`: Grok 4.7 Extra
High). Родитель передаёт область ревью и отдаёт отчёт человеку как есть.
Сам родитель ревью не подменяет и правки по нему не вносит.

## 1. Область

1. Человек назвал файлы, коммит или дифф — ревьюить только это.
2. Иначе взять написанное в текущей задаче:
   - незакоммиченное: `git status`, `git diff`, `git diff --cached`;
   - коммиты ветки, которых нет в `master`: `git diff master...HEAD`
     и `git log master..HEAD --oneline`.
3. Пустой дифф — стоп, сказать, что ревьюить нечего.
4. Читать изменённые файлы целиком и вызывающий код, без которого вердикт
   был бы догадкой. `CONTEXT.md`, раздел «Invariants (don't break)» —
   обязателен. UI-числа и иконки — только если дифф их касается
   (`.agents/skills/develop/references/ui.md`, `references/icons.md`).

Gradle не запускать. Прогон сьюта — зона тестировщика.

## 2. На что смотреть

Сначала дефекты, потом улучшения. Улучшение, которое не сидит в этом
диффе, не раздувать: одна строка «вне области» в конце, без рефакторинга
всего класса.

Ошибки и риски:

- Логика, граничные случаи, пустые данные, повторный вызов, отмена,
  поворот экрана, обрыв на середине записи.
- Инварианты `CONTEXT.md`: minSdk 19 и запрет API выше 19, без AndroidX и
  новых зависимостей, Holo; `upsert` / `upsertBasic` не затирают
  `last_read`; `updateMetadata` не затирает `user_edited`; `Formats.ALL` —
  единственный список форматов; файл книги не остаётся полузаписанным
  (`.copying` → rename, MetaWriter `.tmp` → swap → `.bak`); фильтры
  каталога только на сессию; один зависший файл не блокирует очередь
  обогащения.
- Стиль проекта, если дифф его нарушил: Java pre-lambda (анонимные классы,
  без лямбд и стримов), `NewApi` в `app/lint.xml` — error.
- Дыра в тестах относительно нового поведения — назвать, тест не писать.

Улучшения — только по затронутому коду: мёртвая ветка, дубль, имя, которое
врёт, обработка ошибки, которая глотает сбой, лишняя работа на UI-потоке.
«Переписать иначе» без конкретного дефекта — не улучшение.

## 3. Отчёт

Писать по-русски. Каждое замечание — отдельно, с файлом и местом в коде.
Нет замечаний уровня «ошибка» и «риск» — так и написать.

```markdown
# Ревью

Область: <ветки/файлы или «незакоммиченное»>.

## Ошибки
- `путь:строка` — что сломано, при каком входе, чем кончится.

## Риски
- `путь:строка` — что может сломаться и чего не хватает, чтобы это утверждать.

## Улучшения
- `путь:строка` — что упростить и зачем. Без патча на весь файл.

## Вне области
- Одно предложение, если рядом виден чужой дефект. Иначе раздел опустить.
```

Уровни:

| Уровень | Когда |
|---|---|
| Ошибка | Воспроизводимый дефект или сломанный инвариант на коде, который уже есть |
| Риск | Граничный случай или гонка, для которых в диффе нет защиты и нет теста |
| Улучшение | Код работает, но в этом диффе его стоит упростить |

Не выдумывать симптом. Не уверен — это «риск», и в тексте сказано, чего
не хватило (вызывающий метод, тест, устройство). Предлагать направление
правки в одном-двух предложениях, не подменять ревью готовым патчем.
