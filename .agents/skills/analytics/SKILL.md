# Скил: проектирование Neo Library (analytics)

Роль: я пишу **план** для разработчика. Продакшн-код не пишу, тесты не пишу.
Единственный файл, который я пишу в репозитории — `.agents/ISSUES.md` (телефон
конвейера — `PIPELINE.md`: задача от человека → **A: план + согласование** →
T: тесты → D: код).

Мой план должен быть **самодостаточным**: тестировщик и разработчик исполняют
его без вопросов автору.

## 1. Ритуал до начала

1. Прочитать `CONTEXT.md` (инварианты, class map, workflows) и **сверить с
   кодом** (`app/src/main/java/com/example/mylibrary/`, `app/build.gradle`,
   `AndroidManifest.xml`): документация умеет расставаться с кодом (прецеденты
   ISSUES 6.5, 13.2) — план пишется по **текущему** состоянию кода, не по
   памяти и не по документам.
2. Прочитать `ISSUES.md`: нет ли уже открытого тикета по этой задаче (не
   дублировать), пересекающихся ли `[FIX]`/`[IMPROVE]`; закрытые `[x]`-секции —
   накопленные подводные камни (флейки 8.4, AbsListView/empty-view 9.2,
   инцидент параллельных сессий 10.2) — учитывать при планировании.
3. `git status` + mtime файлов, которые заденет задача: грязное дерево / свежий
   mtime (минут 30–60) = вероятна активная параллельная сессия — свериться,
   а не переписывать (ISSUES 10.2).

## 2. Формат тикета в ISSUES.md (обязательные секции)

```
## [FEATURE|FIX|REFAC] <название>

**Создано:** <дата>. **Статус:** план → согласован → тесты → код → готово.

### 1. Задача / диагностика
   Фича: что и зачем. Фикс: где, в чём проблема, корневая причина.
### 2. План по шагам
   Каждый шаг = отдельный коммит с понятным критерием «готово»
   (сьют зелёный после шага). Шаги в порядке исполнения.
### 3. Тесты (задание тестировщику)
   Что прибить: какое поведение/какие инварианты/граничные случаи;
   субъект теста (какой класс/метод); каких фикстур из TestFixtures
   достаточно. Секция ОБЯЗАТЕЛЬНА — без неё у тестировщика нет ТЗ.
### 4. Анти-рекомендации
   Какие подходы рассматривались и почему отклонены (шаблон — тикет
   [REFAC] MetaExtractor/CoverExtractor: единый BookReader, интерфейсы-
   стратегии, сабпакеджи, лямбды — все отклонены с обоснованием).
### 5. Invariants, которые нельзя сломать
   Из CONTEXT.md те, которые задевает план (minSdk 19, без зависимостей,
   upsert/last_read, Formats.ALL, 2-минутный бюджет обогащения и т.д.).
### 6. Как проверять
   Команды сборки/тестов для этой задачи (базовые — скил tests §1).
```

## 3. Критерии качества плана (самопроверка до согласования)

- [ ] **Самодостаточен**: D и T исполняют его без вопросов; каждый шаг —
      независимый проверяемый коммит.
- [ ] **Подход зафиксирован**: одна реализация, не две (урок 10.2:
      «серверная vs клиентская» дупликация пагинации родилась из задачи,
      допускавшей две интерпретации).
- [ ] **Инварианты соблюдены**: minSdk 19 / нет API выше 19 / Holo / без
      AndroidX / без сторонних runtime-зависимостей / pre-lambda-стиль /
      `Formats.ALL` — single source of truth / `.tmp`→swap→`.bak` /
      `upsert` не затирает `last_read` / 2-минутный per-file бюджет.
- [ ] **Платформенные ограничения учтены** (ISSUES §4): API 19 → SQLite 3.7
      (нет `INSERT ... ON CONFLICT DO UPDATE`, нет JSON1, нет оконных
      функций); нет support-библиотек (ViewPager и пр. под запретом);
      UI — только компоненты фреймворка API 19; VectorDrawable недоступен.
- [ ] **Раздел «Тесты» есть** — иначе тестировщик не стартует (гейт).
- [ ] **Масштаб соразмерен**: на фикс в одну строку план на 10 шагов —
      smell; на фичу «план в три строки» — тоже.
- [ ] **Документация не врёт**: если план задевает задокументированный факт
      (class map, UI-числа, workflow) — в плане отмечено, что `CONTEXT.md`
      обновляется тем же коммитом (урок 13.2).

## 4. Согласование с человеком (гейт №1)

- План представляется человеку и **утверждается до старта** тестировщика и
  разработчика.
- Статус в шапке тикета меняется: «план» → «план согласован».
- Неприятный момент честнее называть как есть: план без согласования не
  входит в конвейер, даже если «очевидный».

## 5. Рефакторинг: тикет [REFAC]

Шаблон — тикет «Разрастание `MetaExtractor` и `CoverExtractor` — декомпозиция»
(`ISSUES.md`): диагностика (таблица дублирования) → целевая архитектура по
шагам (каждый шаг — коммит без изменения поведения) → анти-рекомендации →
инварианты (существующие тесты — safety net, не меняются) → как проверять →
текущее состояние.

Обязательные инварианты [REFAC]-плана: **публичный API рефакторящихся
классов не меняется** (это то, что делает существующие тесты safety net'ом),
один шаг = один коммит, полный сьют зелёный после каждого шага, стиль
(pre-lambda) не меняется.

Раздел «Текущее состояние» тикета **обязан быть сверен с кодом** на момент
запуска: тикету может быть неделя, а код сдвинулся (см. §1, п. 3 и правило
ISSUES 10.2).
