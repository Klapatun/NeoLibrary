### 7.1 Переимпорт под тем же именем при `user_edited=1`: метаданные нового файла не применяются — [ ] (средний)
- **Где:** `MainActivity.importToLibrary` (фикс 6.4, `edf6752`), `BookDatabase.markMetaPending`, `updateMetadata`.
- **Проблема:** при импорте поверх существующего файла сбрасывается только
  `meta_done`, чистится кэш обложки; флаг `user_edited` остаётся. Если
  пользователь раньше правил метаданные СТАРОЙ книги, строка (теперь это
  ДРУГАЯ книга с тем же именем) держит `user_edited=1` → `updateMetadata`
  заполняет только пустые поля → in-file метаданные нового файла не
  применяются, а в каталоге над новым файлом навсегда остаются пользовательские
  значения старой (флаг монотонный, ничего его не сбросит).
- **Доработка:** при перезаписи файла сбрасывать и `user_edited` (редакции
  пользователя относились к старому файлу): добавить сброс `user_edited=0` в
  `markMetaPending` либо отдельный вызов в import-пути. Тест: user-edited книга
  → переимпорт под тем же именем → title берётся из нового файла.

### 7.2 «Recently read» не обновляется во время фоновой обогащённости — [ ] (низкий)
- **Где:** `MetaEnricher.start` (batch-notify), `BookProvider` (`RECENT_URI`).
- **Проблема:** фикс 6.1 ввёл `notifyChangeAll` для delete/edit/markRead, но сам
  bulk-воркер по-прежнему шлёт `notifyChange` только на `CONTENT_URI`. Вкладка
  «Recently read» слушает `RECENT_URI`: пока идёт stage-2, её строки (title
  меняется с имени файла на настоящий, появляется обложка) остаются устаревшими
  до любого другого события (смена фильтра, markRead, правка, удаление).
- **Доработка:** в `MetaEnricher.start` заменить `notifyChange(CONTENT_URI)`
  (batch + финальный) на `BookProvider.notifyChangeAll(appContext)` —
  application-context там уже есть.

### 7.3 Узкая resurrect-гонка осталась в `EditMetaActivity.save` — [ ] (низкий)
- **Где:** `EditMetaActivity.save` (фикс 6.2, `8d5995a`).
- **Проблема:** фикс закрыл широкий случай (строка удалена до `getById`), но если
  её удалят **между** `db.getById(book.id)` и `db.upsert(updated)`, path-based
  `upsert` INSERTит новую строку, и `markUserEdited(updated.id)` пометит уже её:
  книга воскресает под новым id. Окно — миллисекунды, но тот же класс бага.
  Связанно: `upsert` + `markUserEdited` — две отдельные транзакции (см. 1.3).
- **Доработка:** сохранять через id-based update (`UPDATE ... WHERE _id=?`,
  без INSERT-ветки) — resurrect-ветка исчезает совсем.

### 7.5 `startEnrichment()` на UI-потоке при каждой ротации — [ ] (низкий)
- **Где:** `MainActivity.onCreate` (фикс 6.3, `9987668`).
- **Проблема:** `startEnrichment()` → `db.needMeta()`: при каждом пересоздании
  (ротация) на UI-потоке материализуется весь список pending-книг
  (`fromCursor` на каждую строку), хотя нужен только ответ «пусто/не пусто».
- **Доработка:** дешёвый `SELECT COUNT(*) WHERE meta_done=0` (новый
  `hasPendingMeta()`) либо перенос проверки внутрь воркера.

### 1. База данных (`db/BookDatabase`)

#### 1.3 `upsert`/`upsertBasic` не атомарны — [~] (средний, частично закрыт)
- **Где:** открытый остаток — `upsert()`, `upsertBasic()`; закрытая часть —
  `upsertBasicBatch()` (`BookDatabase.java:201`), `updateMetadataBatch()`
  (`:285`).
- **Сделано (PR #14, `17a8c65`, 2026-10-17):** горячие пути — scan
  (`upsertBasicBatch`) и stage-2 enricher (`updateMetadataBatch`) — теперь
  атомарны группами: `beginTransaction`/`setTransactionSuccessful`/
  `endTransaction`, BATCH_SIZE=5, атомарный откат группы.
- **Осталось:** одиночные `upsert()`/`upsertBasic()` (используются
  import-путём, `MainActivity.java:893`) — `SELECT _id` → `UPDATE`/`INSERT`
  без транзакции (статический лок защищает от interleaving, но не от падения
  в середине — может остаться половинчатое состояние, напр. вставленная
  строка без корректного `_id` в модели).
- **Доработка:** обёртка в `db.beginTransaction()`/`setTransactionSuccessful()`/`end()`.
  Примечание: синтаксис `INSERT ... ON CONFLICT DO UPDATE` (SQLite 3.24+) **недоступен** —
  на API 19 стоит SQLite 3.7, см. §4.

#### 1.4 Сироты каталога: файл удалён/перемещён на диске — [ ] (средний)

### 2. Кэш обложек (`util/CoverCache`)

#### 2.2 Ключ кэша — `path.hashCode()` — [ ] (низкий)
- **Где:** `CoverCache.fileFor()`.
- **Проблема:** `String.hashCode()` — 32 бита, коллизии двух разных путей возможны;

### 3. UI / потоки

### 11.2 Подводный камень, найден пробами: OnTouchListener на списке НЕ вызывается

Первая версия вешала observe-only `OnTouchListener` на list/grid
(`setOnTouchListener`) — и регрессионный тест упал: listener не вызывался.
Пробы (Robolectric sdk 19): на голом `View` listener срабатывал, на
`FrameLayout` — тоже, на `GridView` — никогда (при том что событие «обрабатывалось»).
Причина (AOSP 4.4 `ViewGroup.dispatchTouchEvent`): `OnTouchListener` вызывается
только из `View.dispatchTouchEvent`, а `ViewGroup` ПЕРЕОПРЕДЕЛЯЕТ этот метод и
сначала шлёт событие в child под пальцем; кликабельная строка/плитка
ПОГЛАЩАЕТ весь жест (`handled = true`) — до `super.dispatchTouchEvent` (и до
listener'а списка) дело не доходит. Т.е. на реальном устройстве свайп, начатый
на книге, до listener'а списка тоже не дошёл бы — баг был не в тесте, а в
дизайне. Отсюда `dispatchTouchEvent`-override в subclass'ах (он выполняется ДО
dispatch'а в children). **Урок:** OnTouchListener на AbsListView/ScrollView =
мёртвый код для жестиов, начинающихся на child'ах; проверять пробой на голых
View → ViewGroup → целевой вью.

### 11.3 Подводный камень №2: на API 19 свайп ВНУТРИ строки = клик по строке

Вторая итерация (после 11.2) уже перелистывала страницы, но тест «свайп не
открывает диалог» упал: диалог «Open this book?» открывался. Проверено по
исходникам AOSP 4.4 (`View.onTouchEvent`, `AbsListView.onInterceptTouchEvent`):
- в вью внутри скроллящего контейнера DOWN ставит только `PFLAG_PREPRESSED`
  (зажигание press с задержкой), а MOVE снимает его, только когда палец
  ВЫШОЛ за ГРАНИЦЫ вью (`pointInView(x, y, slop)`) — не по расстоянию от
  точки DOWN. Свайп на 150px из x=150 в плитке 242px ширины границ не
  пересекает → на UP `prepressed` ещё стоит → клик постится;
- `AbsListView` перехватывает жест у строки, только когда ВЕРТИКАЛЬНОЕ
  смещение > slop (`startScrollIfNeeded(y)`, x не учитывается) — горизонтальный
  свайп строка удерживает до конца.

Т.е. на реальном 4.4-устройстве горизонтальный свайп по строке, не выходящий
за её границы, тоже открывал бы книгу — баг был бы в проде, а не только в
тесте. **Фикс** (стандартный паттерн swipeable-list'ов): в тот момент, когда
жест пересёк порог свайпа, `PagedListView`/`PagedGridView` перехватывают его
сами (`onInterceptTouchEvent` → true) — фреймворк шлёт строке `ACTION_CANCEL`
(press сброшен, клика не будет) — и глотают оставшиеся события в
`onTouchEvent` (список сам не скроллится/не кликается по горизонтальному
свайпу). Тап и короткая дрожь ниже порога (3×touchSlop) перехвату не
подвергаются — обычные клики по строкам работают как раньше.

### 11.5 Ограничения (улучшения)

- Без слайд-анимации (реалистичный слайд требовал бы второй страничный view /
  своего пейджера — за рамками framework-only API 19); листание мгновенное,
  как у кнопок Prev/Next.
- Шлёпок-флик признаётся только если смещение ≥ 3×touchSlop (без
  velocity-tracking — намеренно: детерминированно и тестируемо).
- Свайп работает по области книг (list/grid); сам пейджер-стрип не свайпается.
